# A3.2 work plan: the network (draft, 2026-11-28)

**Status: draft for the founder to agree.** Nothing here is built. It follows the agreed
networking decisions in `main-chain-design.md` (A3-4) and the deployment plan in
`dual-chain-deployment.md`; the small rules below are proposals.

Today the consensus core (A3.1) runs only inside one test process: messages are values handed
between `Node` objects, and catch-up works only within the recent decision window. A3.2 makes
real processes talk over TCP, first on one machine, then on the three validator hosts next to
v1. Each step is built by one worker, reviewed, shown to the founder, then pushed.

## Steps

| Step | What | Done when |
|---|---|---|
| **N1 Wire format** | frames: length, version, network ID, message type, body; a codec for every message (proposal, vote, decision, sync request, submissions of ranges, primes, transfers, votes, ring messages, block and certificate requests); a size limit per type, checked before decoding | every message round-trips; every truncated, oversized or corrupted frame is refused before any signature check; a fuzz run finds nothing |
| **N2 Validator links** | one process per validator: an event loop that feeds `Node` (receive, tick, deadlines) with a real clock; authenticated, persistent links to the other validators (each side proves its consensus key; protocol version, build commit, network ID and genesis hash exchanged, F12); reconnect with backoff; a bounded send queue per peer; consensus state written to disk before anything is sent | three processes on one machine decide blocks; any one can be killed and restarted and rejoins; a peer with a wrong key, network or genesis is refused at the handshake |
| **N3 Public port** | submissions from miners and wallets, and status; per-client limits (message size, pending submissions per miner, rate); public traffic never shares a queue with validator links (F13); the mempool revalidated after every block (F9) | a flood of junk or oversized submissions from one client does not slow consensus; valid submissions from others still get in |
| **N4 Catch-up from block files** | a node that is behind fetches certified blocks by height in chunks, checks each one (mathematics, hash chain, certificate against the set active at that height), keeps partial progress, retries another peer on failure (F7); uncertified or conflicting local blocks are rolled back (F6) | **a fresh node syncs from genesis** (F18); a node far behind the decision window catches up; a peer serving a bad block is dropped and another is used |
| **N5 Local testnet** | the three validators plus the reference miner on one machine, on local ports; a small relay that drops, delays and splits traffic, so the simulation's crash, partition and restart tests run against real processes; a long run | the simulation's scenarios pass with real processes; a 24-hour run with restarts has no stall and no disagreement; memory and CPU per process measured |
| **N6 Next to v1** | the three servers, as `dual-chain-deployment.md` sets out: a separate service, user, paths and fresh keys; ports 9339–9341; firewall open only between the three hosts; memory and CPU limits; a Next-only rollback | v1 shows no change in progress or memory before and after; Next runs a multi-day rehearsal; stopping Next touches nothing of v1 |

Order: N1, N2, N3, N4, N5, then N6. N1–N5 run on this machine only. **N6 touches the live
hosts and is asked for separately, host by host,** with v1's health checked before and after.

## Small rules (proposed, not agreed)

1. **Framing:** a 4-byte length, then version, network ID, type and body. Unknown versions
   or types are refused, never skipped silently.
2. **No encryption on links for now.** Everything on the chain is public, and proposals,
   votes and submissions are already signed, so a link only needs to prove who is on the
   other end (for priority and limits). An encrypted transport (for example Noise) can come
   as a later version.
3. **Three programs, one shared library** (founder, 2026-11-28):
   - **validator**, for validator operators: the node, catch-up, status and store tools, as
     subcommands of one program, so no helper can go missing (F11);
   - **miner** (reference), for anyone: main-chain and ring mining, submitting to the public
     port;
   - **wallet** (reference), for anyone: keys, transfers, balances; later notes and cash.

   They share one library for formats, checks and signatures, so they cannot disagree on what
   is valid. Miners and wallets never carry validator code, and others may write their own.
   The validator uses one thread for its event loop; heavy checks (certificates, Pratt) are
   bounded in size so a single message cannot stall it.
4. **Persist before send:** consensus state is written and flushed before a vote leaves, as
   the simulation already assumes; files are checksummed and refuse to open when corrupt,
   with no silent recreation (D19).
5. **Ports:** 9339 public, 9340 validator links, 9341 block files (as planned). Startup fails
   if a port is taken; it never falls back to v1's ports or stops another process.
6. **Starting values for the "to be set" parameters** (votable later, D20):
   - 7 inputs per transfer: 1,000;
   - 8 transfers per block and waiting: 10,000;
   - 9 fee by size: none at first (the minimum fee only);
   - 15 message size 256 KB, pending submissions per miner 64.

## What v1 taught (from `v1-lessons.md`)

| v1 problem | Here |
|---|---|
| peer sync fragile: blocked queues, stalled writes, unsafe downloads (7) | bounded per-peer queues with timeouts; blocks fetched by height, verified before they are applied, partial progress kept |
| mempool interfering with sync (8) | the mempool never touches chain state; revalidated after each block |
| connection limits hit by validators (9) | validator links are separate from public traffic, with their own limits |
| fragile caches and sidecar files (10) | one store, checksummed files, no sidecars |
| commit-phase races and retries (4) | not in A3.2: there is no per-integer commit–reveal |

## This server

val1 has about 2 GB of memory and runs v1's validator, whose sync server sometimes grows to
about 1.4 GB. So: builds one at a time under the memory cap, as for B3; the local testnet
(N5) runs each process under its own cap (about 150 MB each to start), and only when enough
memory is free; long runs may need val1 pauses, each asked for separately. On the live
hosts (N6), Next gets a hard memory limit so it can never push v1 out.

## Not in A3.2

The proof-carrying query API and the clients (miner, wallet, explorer) come with the
invited testnet (A4/B4). Ring batches as a consensus decision are B3.6; once that lands, the
network carries ring messages like any other submission. Opening the public port beyond the
three hosts is a separate decision.

## Timing with the ring work

Rings (B3.5–B3.7) and the network share this machine's memory, so their builds alternate.
N1 can start while B3.6 is being reviewed; the consensus code itself is shared, so N2 waits
until B3.6 has landed.
